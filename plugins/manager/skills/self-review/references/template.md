# Self-review structure + the rubric

The review has two halves: a **month-by-month activity log** and a
**rubric narrative**. The log is the evidence; the narrative is the
argument. Keep them consistent — every claim in the narrative should be
visible somewhere in the log.

## Output structure

```markdown
# Self-Review — <Cycle start> → <Cycle end>

*<One line of context: team(s) this cycle, and any role change. e.g.
"Team: <team> all cycle" or "Team A (first half) → Team B (second
half); manager of Team B since <month>.">*

## Monthly Activity Log

**<Month YYYY> — <short project tag>.** One paragraph. Lead with the
project(s), then the concrete outcome. For heavy-code months, put the
merged-PR count in the heading, e.g. "(45 PRs)". Plain and declarative.

... one paragraph per month across the cycle ...

## <Category 1, e.g. Impact>
<Prose mapped to that category's criteria.>

*As a manager (since <month>):* <short sub-paragraph — only if the user
manages people.>

## <Category 2, e.g. Execution>
<Prose mapped to that category's criteria.>

*As a manager (since <month>):* <sub-paragraph, if applicable.>

## <Category 3, e.g. Collaboration>
<Prose mapped to that category's criteria.>

*As a manager (since <month>):* <sub-paragraph, if applicable.>

## <Category 4, e.g. Growth>
<Prose mapped to that category's criteria.>

*As a manager (since <month>):* <sub-paragraph, if applicable.>

**<Extra prompt from the user's form, if any>.** <Some forms ask more,
such as skills built this cycle or how you use AI tools. Answer only
the prompts the user's form includes; omit this block otherwise.>

## Goals & Development

**Goals for next cycle.** <What the user wants to take on, tied to what
the team/org needs.>

**Where I want to develop / how my manager can help.** <Honest growth
edges and concrete asks for support.>
```

## The rubric

Use the company's rubric when the request or a pasted form names it,
with those names as the section headings. Otherwise use the default
below, say so in Assumptions, and ask for the form's categories in the
closing batch. The narrative should hit the
criteria without reciting them — write prose that *demonstrates* them.

The generic default:

### Impact
- Delivered outcomes that mattered to users, customers, or the business
- Chose work with the highest leverage

*Manager additions:* set direction the team could execute on.

### Execution
- Shipped on time with good quality; owned the trade-offs
- Exercised sound judgment and took responsibility for decisions

*Manager additions:* built a focused, effective team; kept delivery
predictable.

### Collaboration
- Worked well across teams and communicated openly
- Mentored, reviewed, and unblocked others

*Manager additions:* gave clear feedback; recognized others' work.

### Growth
- Built new skills and deepened expertise
- Took smart risks and learned from what didn't work

*Manager additions:* grew the people on the team.

## Mapping work to categories

The same project usually supports more than one category. Split by what
it demonstrates. With the default rubric:

- Picking and landing the work that moved a goal → **Impact**.
- Shipping a project end-to-end, hitting dates, owning the trade-offs →
  **Execution**.
- Landing something across many partner teams, working in the open,
  mentoring, running a team → **Collaboration**.
- Learning a new domain, a novel approach, tools others adopt →
  **Growth**.

If the user manages people, the manager sub-notes carry the
manager-specific expectations. Be honest about tenure: a few months of
managing is an *early* track record — frame it that way and let the
user add specifics (a hire, a growth moment for a report, a norm they
set).

## Ratings

The review form may ask for a rating per category. **Do not pick one.**
Leave it to the user and say so. You can note which categories the
evidence most strongly supports, but the choice is theirs.

## House style

- Plain, declarative, active voice. Match the user's anchor docs.
- No em dashes. No buzzwords ("pivotal," "landscape," "groundbreaking").
- Describe outcomes, don't count activities.
- "Created," not "invented."
- Vary sentence length. Let a short sentence land.
