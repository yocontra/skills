# openspec plugin evals

Behavioral tests for the `openspec` plugin, run with
[`claude plugin eval`](https://code.claude.com/docs/en/plugin-evals).

```bash
scripts/run-evals.sh openspec --runs 1 --ablation none
```

The skills and commands, apart from the hand-written `commands/setup.md`, are generated by
`make sync-openspec` from the OpenSpec CLI, so these cases pin routing, plus the one rule the sync adds on top (archive in the PR that lands the work): each request loads the right skill and names the matching
`openspec` CLI step, and a plain coding request loads none. Fix a routing miss upstream
in OpenSpec, never by hand in the generated `SKILL.md`, because the next sync overwrites
it. A fix that cannot wait for upstream goes in the `EDITS` list of
`scripts/sync-openspec.sh`, as the explore description's routing fix does.

| Case | Asserts |
|------|---------|
| `propose-routing` | "Propose a change to add X" loads `openspec-propose` and names `openspec new change`. |
| `explore-routing` | "Think this through with me first" loads `openspec-explore` and writes no code or proposal. |
| `apply-routing` | "Start implementing its tasks" loads `openspec-apply-change`. |
| `update-routing` | "Revise the change's plan" loads `openspec-update-change`. |
| `sync-routing` | "Sync the delta specs, do not archive" loads `openspec-sync-specs`. |
| `archive-routing` | "Archive the finished change" loads `openspec-archive-change` and names `openspec archive`. |
| `archive-in-pr` | A change whose tasks are all done, about to open its PR, is archived in that PR before merge, not in a follow-up after merge. |
| `explore-declines-implementation` | Asked to write code mid-explore, explore mode declines and points at `/openspec:propose`. Pins the explore stance at `effort: medium` after the "Think deeply" and IMPORTANT prose was removed. |
| `setup-routing` | "Set this repo up for openspec and convert our plans" loads the `/openspec:setup` command, uses `openspec init --tools none` and sets `schema: spec-driven-tested`. |
| `setup-existing-changes` | In a repo with changes made under `spec-driven`, setup edits each active change's `.openspec.yaml` and checks it with `openspec status --change`. Only the status check fails on the old command: the model infers `.openspec.yaml` from the prompt. |
| `setup-dropped-plan-cleanup` | A plan dropped mid-setup has the change directory setup created for it removed, and only that one; a change that predates setup stays. |
| `negative-code-request` | A plain coding request loads no skill. |

No case asserts that a propose request writes `test-plan.md`. The `spec-driven-tested`
schema reaches the model only through `openspec status` and `openspec instructions` output,
and no command can run in a case, so the model would name `test-plan` only if the prompt
told it to. That tests the prompt, not the plugin. `scripts/sync-openspec.sh` validates the
schema with `openspec schema validate` instead.

The same holds for the schema's citation rule (cite files and commands, never line numbers or
method names): it reaches the model only through `openspec instructions`, so no case asserts it.

The SessionStart hooks in `hooks/` are not covered here. A case cannot set
`PATH`, so it cannot put a missing or wrong-version CLI in front of `check-cli.sh`, and it cannot
point `install-schema.sh` at a missing, stale or unwritable schema dir. The hooks'
behavior tests are in `hooks/__tests__/`.
